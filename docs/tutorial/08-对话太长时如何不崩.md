# 08 对话太长时如何不崩

**一句话：对话越长越贵、越长越容易超窗口，系统用“三步瘦身”让它既不爆、也不丢缓存。**

> 定位：我们在全局图的“记忆”格，这是后半 —— 太长时怎么瘦身。

## 为什么不能一上来就删旧消息

模型提供方会对“前面没变过的对话前缀”做自动缓存（`src/minicode/providers/openai_compat.py:303` 会读 `cached_tokens`）。如果每轮都去改旧消息，下一次请求的前缀就全失效，等于每轮都从零计费。

所以 minicode 定了一条纪律，写在 `src/minicode/context/manager.py:1` 顶部：

> 两次压缩之间，历史一字不改；要删，只在压缩那一刻删。

平时只做最轻的“截断”，重的“清理”收束到压缩里一起做。

## 三步分别做什么

可以把对话想象成一本越来越厚的笔记本：

**1. 截断（每轮都做，不碰历史）**
模型工具一次吐了几万行怎么办？`context/manager.py:113` 的 `truncate_tool_output` 会调 `tools/truncate.py:48`，超过 `2000 行 / 51200 字节` 就把原文写到临时文件，只在对话里留一句“已写到 `output_path`，其余请读文件”。工具结果变短了，但历史消息本身没被改写。

**2. 清理旧工具结果（只在压缩时做）**
真的要删历史吗？`prune_tool_outputs:131` 才会做，而且有两条保护：
- 最新的 4 万 token 不动（`prune_protect_tokens`）
- 最后一轮模型的回复不动

只有累积到能省下 2 万 token（`prune_minimum_tokens`）才动手，把旧的工具输出替换成一句 `[tool output removed…]`。这个函数只被 `compact:224` 和 `rebuild:323` 调用，平时 `prepare:309` 根本不进这条分支。

**3. 压缩（到阈值才做，会调模型）**
当估算的 token 快用满 85%（`0.85 * max_tokens`，在 `manager.py:309` 判断）时，才做压缩。`_select_split:196` 选一个切点（多轮对话按“用户那句话”切，单轮长轨迹按“模型那次回复”切），保留最近 2 万 token 不动，前面那一截送去让模型写摘要。

摘要经 `templates/COMPACTION_TEMPLATE.j2` 提示词生成，失败则用本地 `fallback_summary` 拼一句，包成 `role: user` 的 `<compaction>...` 消息，插在 `system` 之后。压缩会调一次模型，其余两步都是本地操作。

## 什么时候发生什么

- 没到 85%：`prepare` 直接返回，`pruned_tokens = 0`，历史一个字不改 —— 这是为了保缓存。
- 到了 85%：先做第 2 步清理，再做第 3 步压缩；两个都算在一次“压缩”里，所以是预期的缓存重置点。
- 估算怎么算：`context/tokens.py:29` 故意算得偏大（中文按 1.3 字符/token、英文按 3.6，`Message` 额外 +4、`ToolCall` +12），宁可早压缩也不超窗；真超了还有 `core.py:246` 的 `_force_compact` 兜底。

## 记住什么

截断是每轮的轻量止血，清理和压缩是到阈值才一起做的重瘦身。平时不碰历史，不是偷懒，是让“前面没变的”一直命中缓存、少花钱。
