# 01 这个项目在解决什么问题

**为什么要做 minicode，而不是直接调一次模型？**

## 一个任务需要反复动手

你让模型“修好 `parse_date` 对空串的崩溃”。单次 `client.chat.completions.create` 只能返回一段猜测，看不到文件、跑不了测试。

你需要的是循环：先看文件 → 再改 → 再跑 `pytest` → 看结果再决定。模型提需求，程序去执行，结果再回到模型。这个循环就是全部。

## 三者的位置

`README.md` 第一句点明：用纯 Python 复刻 OpenCode 的核心思路，以 `mini-swe-agent` 的循环为底座。

- `mini-swe-agent` 已有循环与 `bash`
- OpenCode 证明多工具、多权限、多会话、上下文合在一起才可在大仓干活，但为 TypeScript/Bun
- minicode 取后者设计、前者循环，用 Python 重做小而完整的版本，依赖仅 `mini-swe-agent`/`openai`/`anthropic`/`textual`（可选）

## 为何要轻量

轻量不是为了少写代码，是为了让学习者一次只面对一个问题。`pyproject.toml` 的依赖刻意不含向量库与微调链，只留循环、翻译、执行、记忆与边界。少一个依赖就少一条学习路径，你改 `Tool` 时无需懂 `Provider` 的重试，改 `Context` 时无需懂 `TUI` 的线程。

## 一个叶子模块的价值

`src/minicode/project.py` 不依赖项目内任何代码，注释强调“叶子”。

它做两件事。先看根目录的 `pyproject.toml`/`package.json`/`go.mod` 等，推断语言与 `pytest`/`npm test`/`go test` 等命令；再读 `AGENTS.md`/`CLAUDE.md`（`INSTRUCTION_FILES_LOADED`，单文件 20k 截断，`instruction_block`），拼进系统提示词。前者让模型在不同仓库用对命令，后者让仓库的协作约定自动生效。

为何要叶子？若它依赖 `permission`，而 `permission` 又依赖它的 `ECOSYSTEMS` 生成白名单，就会成环。叶子让 `agent`、`permission`、`config` 三处可同时依赖它而不环。同一份判断喂给四处：提示词的 `{{ project }}` 与 `{{ project_instructions }}`、权限的放行列表、配置的生成，避免“建议 `npm test` 却被权限拦”的分叉。

如果去掉它会怎样？模型在 `go` 仓仍会建议 `pytest`，权限仍会放行 `pytest`，系统提示词仍会写“用你仓库的真实命令”，但三者的“真实”各说各话，循环在第一轮就会因“建议与放行不一致”卡住。

## 记住什么

它要解决的不是“如何调模型”，是“如何让模型持续、带权限、带记忆地在真实仓库完成任务”，并用一个叶子模块让“真实”在提示词、权限、配置三处保持一致。
