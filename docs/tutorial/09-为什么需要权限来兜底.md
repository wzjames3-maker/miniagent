# 09 为什么需要权限来兜底

**如何不让 `rm -rf` 被执行？**

> 定位：我们在全局图的安全边界，看 `Agent` 调工具前的最后一道门。

`src/minicode/permission` 独立于 `tools/session/ui`，只答 `allow/deny/ask`，不直接执行。

规则为 `permission/pattern/action`，`pattern` 用 `*`（段内）、`**`（跨段）、`**/`（零级）、`?`（单字），实现在 `policy.py:147`。配置支持 `read: allow` 与 `bash: {"git *": allow}` 双形态，`~/$HOME` 展位在 `ruleset_from_config:215` 处理。

为何要最具体优先？若按“后者全覆盖”，末尾的 `*:ask` 会覆盖 `read:allow`，导致每次读文件都弹框。`_specificity:152` 按是否含通配与长度打分，`read:allow` 的精确 `read` 胜过 `*`，`ALWAYS` 记忆的精确 `pattern` 因此能覆盖配置的宽泛规则，而不会扩大为 `*`。

`PermissionManager:66` 分 `DEFAULT`（`deny→ask→allow`）与 `AUTO`（`--yolo` 下非 `deny` 即放行）；无交互时 `non_interactive` 直接 `PermissionRejected` 而非放行，这是 fail-closed；`ToolRegistry:86` 的 `check_permissions` 逐项 `permission.check`，失败直接包为 `ToolResult` 的 `permission_denied` 回模型，而非抛异常让循环崩。

`BashTool:34` 的 `destructive_targets` 双提取（`shlex` 主 + 正则兜底 `bash -c 'rm …'`）命中则追加 `delete` 二次校验，`default.yaml:27` 双拒 `rm -rf */**`，因为 `*` 不跨 `/`，单条 `rm -rf *` 拦不住 `rm -rf /tmp/foo`。

## 记住什么

最具体优先、`ALWAYS` 仅记精确 `pattern`、显式 `deny` 永不被 `yolo` 放行。
